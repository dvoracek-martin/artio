# Artio commerce extension contracts, version 1

The Core owns commerce state and transaction boundaries. Docker plugins implement external provider behavior through the versioned extension API. The Java interfaces in `artio-extensions` define the semantic model for plugin SDKs and Core adapters; they are not loaded as in-process provider implementations.

The v5.1 [composition contract](plugin-manifest-v2.md) adds explicit per-instance bindings and policy metadata. Payment checkout and shipment creation use the Core-owned v2 router and durable operation ledger when eligible bindings exist. The selected instance, immutable release, configuration generation, account fingerprint, routing scope, method and order obligation are frozen before the remote operation. Capture, cancel, refund, payment reconciliation and carrier tracking use the stored owner; they never select a replacement provider after an ambiguous outcome. Existing v1 environment selectors remain a compatibility path. Payment methods and shipping services/quotes use bounded aggregate reads with explicit partial failures; payment discovery returns ten-minute opaque Core references, and checkout revalidates the reference against the current order and exact provider generation before routing. See P0-06 in the [roadmap](../ROADMAP.md) for implementation and verification status.

## Payment provider

`io.artio.extensions.commerce.PaymentProvider` defines checkout creation, capability discovery, authorization/capture, cancellation, refunds, webhook verification and reconciliation. Set `ARTIO_PAYMENT_PROVIDER=extension` and `ARTIO_PAYMENTS_EXTENSION_PLUGIN_ID` to retain the v1 managed-plugin default. Before calling a provider, Core stores a durable attempt with its obligation, method, stable idempotency key, amount/currency and selected provider instance/release/configuration/account scope. A retry for that same identity resumes the same attempt; an ambiguous result remains `UNKNOWN` and cannot route to a fallback provider. Payment external references are unique within provider, instance and account identity, so separate PSP accounts may safely reuse the same reference string. When v2 bindings exist, `payment.provider.v1/createCheckout` also persists its immutable operation plan before invocation. Capture, cancel, refund and reconcile stay pinned to the persisted owner even if routing priorities or configuration later change. V2 webhook receivers use `/api/v1/payments/provider/bindings/{bindingId}/webhook`; the `verifyWebhook` binding pins signature verification to the configured instance and scope, and Core checks that the verified reference resolves to the same stored release, configuration and account. A webhook that arrives before the checkout row is persisted is retried rather than marked processed. Checkout and financial mutations carry stable caller idempotency keys; Core derives the runtime UUID from the operation and caller key so retries retain the same invocation identity. Admin partial/full refunds require an `Idempotency-Key`; Core locks the payment balance, records completed refund identities, and only increases cumulative refunded amount after the provider confirms the exact amount and currency. Webhook verification receives the unmodified request bytes encoded as Base64 and a Core-allowlisted header map. The allowlist currently includes `Provider-Signature`, `Stripe-Signature`, and PayPal's transmission ID/time/signature, certificate URL and auth algorithm headers; arbitrary headers such as cookies and authorization are never forwarded to the plugin. Providers validate their own signature using these headers and their encrypted configuration. Responses use the corresponding `PaymentProvider` record shapes; reconciliation wraps an optional result in `result`. Providers return their own reference and a neutral state; Core applies it inside its own transaction. Webhook event identity is namespaced by provider and deduplicated before applying order changes. Providers may omit operations through their capability declaration. Checkout expiry is optional and expressed as a duration. The default provider is `none`, and Core exposes no Stripe-only public webhook route.

The reference TWINT plugin is a separate Artio plugin ID (`payments.twint`) backed by the shared Stripe extension image. It restricts Stripe Checkout's `payment_method_types[]` to `twint`; merchant-side Stripe/TWINT eligibility remains controlled by the merchant's activated PSP account. It is not a direct TWINT connector and does not replace PSP onboarding.

`POST /api/v1/payments/methods` accepts `{country,currency,amount?}` and returns only a short-lived `reference` and shopper-facing `displayName` for each eligible option, plus partial-failure metadata. `POST /api/v1/payments/orders/{orderId}/checkout-session` accepts `{methodReference}`. Core resolves the opaque reference, checks its expiry, market and optional amount, rediscovers current eligibility, and requires the same provider instance/release/configuration and method before creating checkout. A retry for the same order/provider/method reuses its stable idempotency identity. Choosing another method or provider gets an independent attempt and does not silently replace an ambiguous earlier attempt.

The Core retains inventory reservation and compensation guarantees. A provider response never directly writes order state. The Core verifies ownership and current state, then applies a single idempotent transition. Provider retries reuse the original idempotency key.

Settlement evidence is mandatory for a captured webhook or reconciliation result: plugins return the provider reference, exact decimal amount, and ISO currency. Core records each verified capture in an immutable `payment_settlements` ledger and on the payment's `captured_amount`/`captured_currency` before deciding whether it can settle the order; `payments.amount` remains the original obligation. Exact captures transition the order at most once. Late captures after cancellation, a second successful attempt after the obligation was paid, overpayments, underpayments and currency mismatches open durable reconciliation cases instead of dropping genuine funds or retrying a new charge blindly. Underpayments and currency mismatches put the payment in `CAPTURE_REVIEW` and block another checkout until resolved. Refund limits and reporting use the actual captured amount when known, so an administrator can return a full overpayment; a full refund resolves that payment's open cases. An overpayment that covers the obligation marks the order paid and preserves the full received amount in the settlement ledger. Administrators can inspect open cases through `GET /api/v1/admin/payments/reconciliation-cases`. Settlement values are never rounded or inferred from order totals.

Provider transaction references are stored separately from checkout/dispute references and are unique within the payment's provider, instance, and account namespace. Signed dispute and reversal events append immutable `CHARGEBACK_OPEN`, `CHARGEBACK_WON`, `CHARGEBACK_LOST`, or `PAYMENT_REVERSAL` evidence. An open chargeback moves a captured payment to `CAPTURE_REVIEW` and blocks refunds until the dispute resolves; a won dispute restores the captured/refunded state only after resolving its matching case, while a loss or provider reversal reduces the remaining refundable balance and remains visible as an operator case. A refund can never exceed `captured_amount - refunded_amount - reversed_amount`. Standard reports expose captured, refunded, reversed, and net amounts separately; paid-item rankings retain refunded orders but exclude funds removed by a chargeback/reversal. The development database remains a single V1 clean-install snapshot.

Checkout rejection semantics are also provider-neutral. A payment plugin may return HTTP `400`, `401`, `403`, `404`, or `422` from `createCheckout` only when it guarantees that no remote checkout session or charge was created. Core maps those responses to `CheckoutRejectedException`, marks the still-pending order cancelled, marks pending payments failed, releases reserved inventory, records the order timeline event and customer notification, then returns HTTP `422`. HTTP `408`, `409`, `425`, `429`, `5xx`, timeouts, transport errors and invalid plugin responses are never treated as definitive rejection: the order and reservation remain recoverable and retries use the same idempotency key. Plugins must not use a definitive status for an outcome whose side effects are unknown.

OpenAPI documents the checkout endpoint's `200` success, `422` definitive rejection, `502` ambiguous provider outcome and `503` missing-provider responses using the shared versioned `ApiError` schema for errors. Clients should retry `502` with the original checkout idempotency identity; `422` indicates the order was cancelled and needs a new checkout.

## Shipping provider

`ShippingProvider` defines method discovery, quotes, shipment creation and tracking, with explicit geographic coverage and capability flags. Set `ARTIO_SHIPPING_PROVIDER=extension` and `ARTIO_SHIPPING_EXTENSION_PLUGIN_ID` to retain the v1 managed-plugin default. V2 `listMethods` and `quote` use bounded aggregate reads; method IDs are namespaced by provider instance, and a quote executes only through the selected eligible instance. With v2 bindings, `shipping.provider.v1/createShipment` selects one instance and persists its release/configuration/account identity and scope on the shipment before fulfillment continues. Tracking for that shipment uses the pinned instance. Checkout exposes `/api/v1/cart/shipping-methods` and `/api/v1/cart/shipping-quote`, then revalidates the selected method and stores the accepted amount, structured delivery address, method and parcel weight in the order snapshot. Backoffice shipment creation uses a stable per-order idempotency key; the returned PDF label is retained on the order and served through an authenticated, size-bounded PDF endpoint. A carrier may implement quotes without label creation, or tracking without shipment creation. Country availability is discovery metadata and does not prevent a merchant from configuring another compatible market. When extension mode is disabled, checkout uses the configured flat shipping amount and Backoffice accepts manually entered tracking numbers.

## Notification transport

`NotificationTransport` sends an already persisted message and returns an accepted/rejected result. Core owns the transactional delivery outbox, retry schedule, dead-letter state and redaction; provider implementations run only in Docker plugins. The default provider is `none`, so absent/disabled plugins leave messages queued without consuming attempts and never prevent checkout or order creation. An installation can select an enabled Docker plugin by setting `ARTIO_EMAIL_PROVIDER=extension` and `ARTIO_NOTIFICATIONS_EXTENSION_PLUGIN_ID`; the plugin declares `notification.channel.v1` and `notifications.send`, then implements the bounded `deliver` operation with the stable delivery ID as its idempotency key. The Brevo reference source is under `artio-plugins/brevo-email`; image publication and provider acceptance are not claimed.

## Search provider

`ProductSearchProvider` indexes and removes catalog documents and returns product identifiers for a query. The Core remains authoritative for catalog data and hydrates current product and locale data from PostgreSQL. Configure an enabled Docker provider with `ARTIO_SEARCH_PROVIDER=extension` and `ARTIO_SEARCH_EXTENSION_PLUGIN_ID`; the plugin declares `catalog.search.v1` and `catalog.read`. It implements `index`, `remove`, `search`, and the generation rebuild operations. Catalog browsing remains independent; search requires an enabled search provider. The source implementation is in `artio-plugins/opensearch-search`; its manifest is not installable until both image digests are published and verified. The legacy in-process adapter remains a local-development fallback.

## Event transport

`EventTransport` publishes events already committed to the Core outbox. The Core's PostgreSQL transaction is the durability boundary. Kafka is required in the standard Artio installation; producer outage leaves events in the PostgreSQL outbox for retry and does not roll back a committed commerce operation. Event contracts carry a stable event ID, event type, schema version, occurrence time, aggregate identity and correlation metadata. Consumers use an inbox/deduplication key and acknowledge only after their database effects commit.

## Runtime mapping

Plugin manifests name the supported `extensionPoints` and permissions. Core invokes plugins over the authenticated Docker runtime API with bounded request/response sizes and timeouts. Each point maps to one request and response schema. Provider credentials are passed only through encrypted plugin configuration and are never part of requests, logs, or returned configuration. Plugins cannot connect to the Core database. See [plugin manifest v1](plugin-manifest-v1.md) for image pinning, geographic availability, and configuration rules.

These contracts do not claim that the reference Stripe, Swiss Post, notification, search, or Kafka plugin images have been built and published. The source package `artio-plugins/opensearch-search` implements this contract as a digest-pinned two-image bundle with persistent sidecar storage and generation-based alias swaps. Its manifest remains a release template until published image digests are available; the older in-process OpenSearch adapter remains a local-development fallback. Publishing reference plugins and completing Docker-backed end-to-end workflows remain in the Phase 2 ledger. Core has no SMTP dependency or provider implementation.
