# Order returns API v1

Artio separates merchandise returns from payment refunds. A return request tracks which order lines a customer intends to send back; the payment refund API independently records provider-confirmed financial movements.

## Customer routes

`POST /api/v1/orders/{orderId}/returns` creates a return request for an authenticated order owner. It requires an `Idempotency-Key` (1–128 characters) and a body with a nonblank `reason`, optional `customerNote`, and 1–50 `{ "orderItemId": "…", "quantity": 1 }` lines. The order must be shipped, delivered, or already partially returned. The server checks order ownership and verifies each line belongs to the order. Quantities already requested, approved, or completed are reserved against the original purchased quantity. Repeating a key with identical lines returns the existing request; reusing it with a different order or line set returns `409`.

`GET /api/v1/orders/{orderId}/returns` lists return requests only for the authenticated order owner.

`GET /api/v1/orders/{orderId}/items` provides the order line identifiers needed to create a return request; it is restricted to the owner. The Storefront order history exposes shipment history and a customer return request flow for eligible order states.

## Staff routes

- `GET /api/v1/admin/orders/{orderId}/returns` lists requests for an order. ADMIN or SUPERADMIN is required by the `/api/admin/**` authorization rule.
- `POST /api/v1/admin/orders/{orderId}/returns/{returnId}/review` accepts `{ "approve": true|false, "note": "…" }`. Only `REQUESTED` requests can be reviewed. Repeated identical decisions are safe; opposing or later decisions return `409`.
- `POST /api/v1/admin/orders/{orderId}/returns/{returnId}/receive` accepts `{ "restock": true|false, "warehouseId": "…", "note": "…" }`. Only approved requests can be received. When restocking is selected, a warehouse is mandatory and the returned variant quantity is received through the inventory application service in the same transaction. Receipt is idempotent after completion. A full return changes fulfillment status to `RETURNED`; partial returns leave the order's fulfillment state intact.

In Backoffice order details, active warehouses are loaded from the inventory API and offered in a selector for the restock action. Staff choose explicitly between Receive & restock (requires an active warehouse selection) and Receive without restocking; the latter is a separate action and is not inferred by dismissing a confirmation dialog.

Every request, decision, rejection, and receipt is recorded in `order_return_events`. Return line restock warehouse and timestamp are retained. Each restock writes an inventory movement with the return UUID as its reason and the authenticated staff member as actor. Refunds are never initiated implicitly: staff use the separate idempotent payment refund endpoint after receipt/inspection as appropriate.

## State model

```text
REQUESTED -> APPROVED -> COMPLETED
     |                     (optional inventory restock)
     +------> REJECTED
```

The current API does not impose an arbitrary return-window policy. No physical carrier label is generated by this workflow; carrier-specific reverse logistics remains a shipping-plugin capability to be connected separately.

## Order timeline and staff notes

The authenticated customer can read customer-visible events at `GET /api/v1/orders/{orderId}/timeline`; ownership is enforced and internal notes are excluded. ADMIN/SUPERADMIN can read the full timeline at `GET /api/v1/admin/orders/{orderId}/timeline` and add an internal note at `POST /api/v1/admin/orders/{orderId}/notes` with `{ "message": "…" }` (1–2000 characters). Order creation, shipment, delivery, returns, refunds and staff notes are recorded transactionally with their business operation where applicable. Internal notes and staff return decisions are not exposed to customers.

Carrier updates can be refreshed by staff at `POST /api/v1/admin/orders/{orderId}/tracking/refresh` when the configured shipping plugin advertises tracking support. Unsupported carriers return `503`; Artio does not fabricate a tracking result. Valid updates are stored in `shipment_tracking_events` and the order timeline. Carrier `DELIVERED` updates transition shipped orders to delivered. Staff can read the bounded history at `GET /api/v1/admin/orders/{orderId}/tracking`.
