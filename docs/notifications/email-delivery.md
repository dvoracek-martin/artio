# Order email delivery

Checkout writes the in-app order notification and an email delivery row in the same PostgreSQL transaction as the order. A rollback therefore cannot leave a notification for an order that was not created. The delivery row contains the user and order identifiers plus message content; the recipient address is loaded from the active user record when a worker claims the row.

Sending is opt-in. Core owns notification templates, the PostgreSQL delivery outbox, retry schedule and dead-letter state; provider clients run as Docker plugins. To use the Brevo reference plugin, enable/register/configure/enable `notifications.brevo`, then set `ARTIO_EMAIL_ENABLED=true`, `ARTIO_EMAIL_PROVIDER=extension`, and `ARTIO_NOTIFICATIONS_EXTENSION_PLUGIN_ID=notifications.brevo` for the event worker. The plugin's API key is write-only and encrypted by Core. The poll interval is controlled by `ARTIO_EMAIL_POLL_INTERVAL_MS` and defaults to 30 seconds. With email disabled or no transport plugin selected, pending rows remain queued without consuming attempts.

The worker claims up to 25 rows with `FOR UPDATE SKIP LOCKED`, uses a five-minute claim lease, and retries failures with exponential backoff from 30 seconds up to one hour. After 12 failed attempts it sets state `DEAD`. The outbox stores only the error class, not exception text. Successful and terminal records have their subject and body redacted. Account erasure marks pending/in-flight records terminal and clears message content.

Delivery is at least once. A provider can accept a message while the worker loses the response; after the lease expires, Core may retry and cause a duplicate. The Brevo adapter sends the stable delivery ID as a provider header, but does not claim exactly-once delivery. Monitor `notification_delivery_outbox` counts by `PENDING`, `PROCESSING`, and `DEAD`; delivery-history UI and retention policy remain future work.
